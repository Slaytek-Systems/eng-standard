# Changelog

Versions follow the commit titles on `main` (`vX.Y.Z: ...`). Minor = new command, config or policy area; patch = rule or doc addition to an existing area. History before 0.7.1 is in `git log`.

## 0.23.1 (14 Nov 2026)

**`eng run --by <id> -- npm test` finds the dependencies** (Core task p579jtt1jzw1pgbxqs0gn9373s8j0kt5). `eng run`'s private worktree holds tracked files only, so `yaml` and `semver` did not resolve there and a bare `npm test` failed on a missing module. Every verifier recorded `sh -c 'npm ci && npm test'` instead.

- **The checkout's `node_modules` comes along when the lockfiles match.** Before the command starts, eng compares every lockfile (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `bun.lockb`) in every folder of the run's commit, workspaces included, with the checkout's copy. When all match byte for byte, eng mounts each of the checkout's `node_modules` folders (the root's and each workspace's) at the same place in the worktree with `fuse-overlayfs`: no download and no copy. The command runs exactly as given and is recorded as given.
- **Nothing the run does reaches the checkout.** The checkout's folder is the mount's read-only lower layer; every write, install, removal or `chmod` lands in an upper layer inside the round and goes with it. eng unmounts before it removes the worktree, on a pass, a failure, a timeout or a signal. Rejected, with measurements: hard links (`cp -al`), because a real `npm install` inside the run rewrote the checkout's `node_modules/.package-lock.json` through the shared inode; a symlink, because `npm ci` through it emptied the checkout's `node_modules`; a full copy, because `node_modules` can reach 2.9 GB. On an 884 MB `node_modules` (22,233 files) the mount took under 10 ms.
- **Otherwise eng says why.** When a lockfile differs, is at the commit but not in the checkout, or is in the checkout but not at the commit; when the checkout has no `node_modules` or the commit tracks one; or when `fuse-overlayfs` is missing or fails, eng prints one line naming the cause and `eng run -- sh -c 'npm ci && npm test'`, and the command runs without it. A repo with no lockfile sees no change.
- `docs/self-merge.md` shows the checker's command as `eng run --by <id> -- npm test` again. `sh -c 'npm ci && npm test'` still works. **Upgrade:** zero manual edits.

## 0.23.0 (14 Nov 2026)

**A verifier's PASS doesn't count while its own run on that head is still going** (Core task p574yb0qyj3n9xyd3tad1h4mg98j3wpy, decision nd7ebz69qb0c39691a3ab586t58j4qwc, Matt, 14 Nov 2026). The 12 Nov sweep found opencode-deepseek posting PASS and then its own FAIL on the same head three times, 1, 1 and 5.5 minutes apart, and self-merge fired 33 s after the deciding PASS on #73. Only prose in the briefs stood in the way. Now a rule in `lib/self-merge.mjs` does. There is still no wait after a verdict: a PASS followed by a newly started probe's FAIL can still merge, a gap Matt accepted knowingly.

- **A PASS does not count while its verifier still has a run in progress on the head.** `eng run --by <id> -- <cmd>` sets commit status `eng-run/<id>/<8 hex of the command>-<run id>` to pending on the run's commit when the command starts, and to success or failure when it ends. The run id is random per run, so two runs of one command by one verifier never share a context and one's end never clears the other. Self-merge reads every page of the head's statuses (more than 100 contexts included) and does not count `<id>`'s PASS while any of its runs is pending; the reason names the context and its deadline. Only a clone whose `origin` is on github.com posts these; a post GitHub refuses is reported on stderr and the run goes on.
- **Who owns a run, who ends it, and when a dead one stops counting.** A run's owner is the account that posted the first pending status on its context (the lowest GitHub status id). Only the owner, or a `ship.self_merge.verifier_logins` login, can end it, with a higher status id; any other account's status on that context is ignored, so a foreign pending (one with a short timeout included) followed by a foreign `success` changes nothing. A run whose `eng` died stops counting at its deadline: the budget timeout its owner's first pending status starts with (1800 s by default) plus 5 minutes after GitHub recorded it. A pending status whose timeout cannot be read never expires by time: no default stands in for a budget that could be longer. The verifier can end it sooner by posting `error` on that context with the same `gh` login (`docs/self-merge.md`). Anyone with push access can still post a pending status and hold a PASS back, as with the `hold` label.
- **Every status row parses in one strict shape, or the merge is refused** (decision nd71xqrdrqemzemfahkpcyvyz18j5gp8). `decide()` parses the head's statuses once, up front (`parseStatuses()`): every row needs a positive whole-number `id` (unique in the list), a `state` of `pending`, `success`, `failure` or `error`, a non-blank `context`, ISO `created_at` and `updated_at`, a `creator` with a login (`null` only off a run context, as GitHub shows a deleted account) and a string or `null` `description`. A row that fails any of these refuses the merge and the reason names it. Rows are ordered by GitHub's status id only, never by time, and the `verdict` status is the row with the highest id on that context. Before, a null row was skipped, a later row with a garbled state passed for a run's end (comment 6866341118), and a run row with no id was ordered by its whole-second time, so an earlier end cleared a later pending run and self-merge read WOULD MERGE. A run whose first pending has no creator now refuses instead of waiting for a listed login.
- **A blank context, or one that looks like a run's but does not parse, refuses the merge.** Every row is checked before any is skipped. A context that, folded to lower case with everything but letters and digits removed, starts with `engrun` must parse in full as `eng-run/<id>/<8 hex>-<run id>`. Before, a blank context, `eng-run/` alone or `eng-run/<id>` with no suffix was skipped as an unrelated status, so self-merge could merge with that row on page two (comment 6867018457). `eng run` now refuses a `--by` with a `/` or a space, which no run status can carry.
- **A run that ends runs self-merge again.** A finished `eng-run/...` status starts self-merge for its head, so a PASS held back by a run counts as soon as the run ends.
- **The run status says it is no merge check.** `timeout 1800s; eng run <id>: running; not a merge check: <cmd>`, then `eng run <id>: finished, exit N; not a merge check: <cmd>`. The timeout comes first, so GitHub's 140-character cut only ever drops the tail (a long id or command). A failing run stays `failure`.
- **The checker's command installs dependencies.** `eng run`'s worktree holds tracked files only, so `docs/self-merge.md` now shows `eng run --by <id> -- sh -c 'npm ci && npm test'`.
- **Rule text.** `AGENTS.md` and `docs/self-merge.md` describe the run guard and the accepted gap. "There is no wait" stays.
- **Upgrade:** zero manual edits. Verifiers keep running `eng run --by <id> -- <cmd>`; with a GitHub `origin` and a `gh` login it now also posts the run status.

## 0.22.0 (12 Nov 2026)

**A pull request's gate runs less** (approved by the repo owner on 10 Nov 2026, after a 45-minute PR gate in a repo with 60 checks run one after another, 3 times each; issue #60). Every new setting is opt-in, and a repo that sets none of them runs and renders exactly as in 0.21.0.

- **`eng gate --event pr|main`.** `--event pr` marks a pull request's gate. `--event main`, or no `--event`, is every other run, `eng run --by` and `eng verdict` included, and keeps the full rule. Any other value is an error and runs nothing. `--base <ref>` names the PR's base; the default is the CI's PR base branch (`GITHUB_BASE_REF`, `BUILDKITE_PULL_REQUEST_BASE_BRANCH`), then `project.default_branch`, as for `eng e2e --required`.
- **`verification.flake_runs_pr`.** `--event pr` runs each check this many times (default `flake_runs`). It must be a whole number from 1 to `flake_runs`, so it can only lower the count. A PR cannot act on a flake, because a flaky check fails the PR either way; main's run after every merge still runs `flake_runs` times and catches it. The gate prints which count it used: `each runs 1 time (verification.flake_runs_pr, --event pr)`.
- **`verification.pr_checks: affected`.** `--event pr` runs only the checks whose `# covers:` paths the change touched: a changed path equal to a covered path or under a covered folder, committed or not, and both paths of a rename. Every other check shows as `unaffected` and does not fail the gate. It fails closed: a check with no `# covers:` line always runs, and every check runs when `eng.config.yml`, `.eng/lock.json` or anything in `checks_dir` changed, when the diff is empty, or when eng cannot compute it (a shallow clone, a base that is not fetched). The gate prints why. A check named on the command line (`eng gate check:<id> --event pr`) always runs. Default `all`.
- **Fix round 1: a PR never skips a check its change affects.** Paths come from `git -z` (non-ASCII, tab, space and unstaged names all match). Every `# covers:` line in a check counts. `..` in a covers path is normalised (`other/../src` is `src`), and a path that leaves the repo fails the check with a clear error. A `--base` that is not the PR's target commit (`GITHUB_BASE_REF`, else `project.default_branch`) runs every check. `# covers:` must name every path the check reads, its helper scripts and fixtures included, or a change to them skips the check. `--event=pr` is accepted. A repo with none of the new keys prints no `checks:` line. **Documented limit:** covers paths split on whitespace, so a path containing a space cannot be named.
- **`verification.parallel: <n>`.** A whole number runs at most n checks at once, side by side while their budgets fit. `true` now means at most 4 at once (before: as many as the budgets fit). `false` or unset still runs them one after another.
- **`# serial: <why>`.** A check that must not run beside another (fixed ports, containers, one shared database) declares it in its header. Under `verification.parallel` it starts only when nothing else runs, and nothing starts beside it. An empty reason fails the check. One after another, it changes nothing.
- **Rendered text.** With `flake_runs_pr` or `pr_checks` set, SHIPPING.md adds what a PR runs and that main runs every check `flake_runs` times. With `verification.parallel` set, SHIPPING.md states the cap and `# serial:`. Unset, both render byte for byte as in 0.21.0 (`test/profile.test.mjs`).
- **Fix round 2: a repo with none of the new keys gates exactly as in 0.21.1, stacked PRs included.** `eng e2e --required` (and the `e2e` gate step) keeps 0.21.1's diff and base handling: a stacked `--base` or `ENG_BASE` decides e2e as before. The stricter base rule applies only to `pr_checks: affected` selection (round 2 also let a stack base select there; round 3 reverses that). A refused base says so, not that the diff cannot be computed. `checks_dir` is normalised the way the gate opens it (`.eng//checks`, `other/../.eng/checks`, `./.eng/checks/` are `.eng/checks`), so a change to a check always runs every check; under `pr_checks: affected` a `checks_dir` that leaves the repo is a config error. Under `pr_checks: affected` a glob in `# covers:` fails with "globs are unsupported" (without it, the 0.21.1 stale message stays), and SHIPPING.md states that covers paths cannot contain spaces or globs.
- **Fix round 3: only the PR's target selects, and covers read as in 0.21.1 without the keys.** Round 2's stack-base rule is reversed: no local base can be proven to be a stacked PR's fork point, and a base on the PR's own branch (its own commit, its branch name, `HEAD`) hid committed changes once one path was dirty. Under `pr_checks: affected` only a base that resolves to the PR's target commit (the CI's PR base branch, else `project.default_branch`) selects; any other `--base` or `ENG_BASE`, a parent PR's branch included, runs every check and the gate names the base. **Documented limit:** a stacked PR selects only in CI, where its target is the parent branch; locally it runs every check. With none of the new keys, `# covers:` is read exactly as in 0.21.1 (the first line, as written); every-line unioning, `..` normalisation and the outside-repo and glob errors apply only under `pr_checks: affected`. `--base=<ref>` is accepted like `--base <ref>`, and the config template states that globs are not expanded.
- **Fix round 4: selection follows symlinks.** Git names a symlink, never its target, so a symlinked check, checks dir or covered path whose target alone changed was skipped. Under `pr_checks: affected` each path the selector compares (the checks dir, each check file, each `# covers:` path) now matches a changed path either as written or through its real paths: the path resolved through every symlinked folder, plus the real path of each symlink git tracks under it. A change under the checks dir's real paths (a symlinked check's target included) runs every check, as a change to a check already did. A changed path that is a folder on the way to a compared path (a retargeted symlink such as `lib -> v2`) counts too. A check whose file or covered path resolves outside the repo or cannot be resolved (dangling, looping) runs on every pull request. Selection only gains checks from this; with none of the new keys nothing changes. `eng gate`'s usage now says only the PR's target selects. SHIPPING.md states that symlinks are followed. Round 5 replaces this tracing.
- **Fix round 5: symlinks are not traced; a symlink fails closed.** Round 4 followed each link to its final target only, so retargeting a middle hop of a chain (`a -> b -> src/a`, a checks dir `.eng/checks -> ../cdir -> v1checks`, `lib -> mid -> v1`), a check's target that became a link, or a git-ignored link inside a covered folder still skipped an affected check while the PR gate passed. The real-path tracing is gone. Under `pr_checks: affected`: a change that adds, removes, retargets or changes the type of a symlink anywhere (git mode 120000 at the merge base, at HEAD, in the index or worktree, or a changed path, untracked included, that is a link on disk; a git-ignored link is never a changed path, and is caught only inside a covered path or the checks dir, below) runs every check and names the path. A checks dir that is, holds or goes through a symlink (a symlinked check included) runs every check. A check whose `# covers:` path is a symlink, goes through one, or is a folder holding one anywhere below it, ignored and untracked links included, runs on every pull request. eng reads this from disk with `lstat` and never follows a link; a folder too large to scan (over 200,000 entries) or an unreadable path counts as holding a link. Selection only gains checks over round 4. A covered folder holding links (for example `node_modules/.bin`) therefore always runs its check. With none of the new keys nothing changes.
- **Fix round 6: a path that is not canonical is never normalised for selection; doctor lists the PR gate; the revert claim is conditional.** Round 1 normalised `link/../src/a` to `src/a`, but on disk it is `other/src/a` when `link -> other/nested`, so the link hop vanished and a change under its target skipped the check while the PR gate passed. Under `pr_checks: affected` a `# covers:` path that is not canonical (a `.` or `..` segment, `//`, a leading or trailing `/`, a backslash) now always runs its check, and a changed path that is not canonical runs every check. Selection reads each covers path as written (normalised only to test that it exists) and checks it for symlinks segment by segment as written. The `checks:` line names each check that runs for another reason than a changed covered path, with the reason: no `# covers:` line, a non-canonical path, a symlink, a folder over 200,000 entries, an unreadable path, or named on the command line. `eng doctor` lists `verification.flake_runs_pr` below `flake_runs` and `verification.pr_checks: affected` under "Gates below the standard default", with restore lines. SHIPPING.md no longer says a failing check on main is reverted unless the repo runs `merge.auto`, whose `eng merge post` opens the revert; elsewhere it says the check turns main red.
- **Upgrade:** zero manual edits. To use it, set the keys and pass the event from CI, for example `eng gate checks --event pr` on `pull_request` and `eng gate checks --event main` on a push to main. A repo whose CI checks out one commit needs enough history for the merge base (`fetch-depth: 0`); without it every check runs. A repo on `parallel: true` with more than 4 checks that fit side by side now runs 4 at a time; set a number to keep more.

## 0.21.0 (12 Nov 2026)

**A repo-level guard blocks what damages this repo's history or work before the command runs** (Safe YOLO lite, Matt, 11 Nov 2026). Since 0.19.0 the AGENTS.md block says hooks, `eng lint`, `eng gate` and CI enforce the repo's rules and name the route when they block. The git hooks only saw a forced push after the fact, and nothing saw `--no-verify`, `--admin` or a discard of local work. Now `eng sync` renders a small guard into `.eng/guard`, and Claude Code, Codex and Cursor run it before each shell command. Matt's machine-wide Safe YOLO keeps everything else (deletes outside the repo, deploys, credentials, network exposure); both can run, and any deny wins.

- **What it blocks, each with its route in the message.** One table of destructive git forms, `DESTRUCTIVE` in `lib/guard.mjs`, with the same table in `docs/lifecycle.md` (a test keeps them in step). In any shape: a forced raw `git push` (a force flag, the lease forms, `--mirror`, a `+` refspec) on any branch in both `git.rewrite_pushed` modes, deleting a protected branch, `git push --prune`, `--no-verify` on any git command but the read-only ones, `git commit -n`, `core.hooksPath` overrides, `git worktree remove --force`, `git clean` without `-n`, `git stash drop` and `clear`, any `git update-ref`, a forced `git fetch` or `git pull` into a local branch (`+main:feat`). Alone at the root, and only when they would lose work: `git reset --hard`, `--merge` and `--keep`; `git checkout -f` and `git checkout` with paths; `git switch -f` and `--discard-changes`; `git restore <paths>` (not `--staged` alone); `git rm -f`; `git branch -D`, and the forms that move an existing branch (`git branch -f`, `-M`, `-C`, `git switch -C`, `git checkout -B`, `git worktree add -B`), of a branch whose tip no other branch holds, local or remote (its upstream counts; a branch the same command drops or moves does not, the default branch included, and a symbolic ref never does). `git reset --hard`, `git checkout -f`, `git switch -f` and a checkout or restore from a commit also count untracked files, which they overwrite (not ignored ones; `git stash push --include-untracked` keeps them). Any unique prefix of a long option counts as the option (`--har`, `--del --forc`), as git accepts it, and a flag that makes a form safe is read last-wins, so `git clean -n --no-dry-run` deletes and is denied. Also `gh pr merge --admin`, and editing the guard: its files and eng's hook entries. Nothing else is blocked.
- **Treated like skill folders.** eng never writes into `.codex` or `.cursor`. It renders `.eng/guard/codex-hooks.json` and `.eng/guard/cursor-hooks.json`, and `eng doctor` prints a Guard section: per tool, wired or not, and the one `ln -s` or the exact entry that wires it. Claude Code's PreToolUse hook goes into `.claude/settings.json`, which eng already renders in full; the deny list stays. Codex runs a repo hook only in a trusted project and after you trust it once in `/hooks`.
- **Fails open on its own errors, closed on what it cannot read.** Node built-ins only, writes nothing, and allows the call on its own error with a note on stderr, so a guard bug never blocks work. The verify rounds found a new parser gap each time (round 5: `$'--hard'`, `bash -o pipefail -c`, `<(git reset --hard)`, `--har`), so the sixth closes the class instead: a command that mentions git and uses any construct the parser does not model (`$'...'`, `$"..."`, `<( )`, `>( )`, `${...}` beyond `${NAME}`, a backslash inside backticks, an unterminated quote, `eval`, `exec`, `trap`, `alias`, `case`, a nested shell with any option but one `-c` word or reading stdin, other shells, `env -S` with escapes) is denied with the route: run the git command as its own command, with literal words. The verb-aware rules apply only to fully modelled commands, so read-only git (`grep -e --no-verify`, `config --get-urlmatch`, `log`, `diff`) works in any shape. A word the guard cannot know (a variable, substitution, glob, brace expansion, `xargs` input) in a git subcommand with a destructive form or hooks is denied the same way; `git push origin HEAD` replaces `git push origin "$(git branch --show-current)"`. A command name made from a variable given a git subcommand is read as git, a program given `git` as a separate word (`strace git ...`, `eng run -- git ...`) is read as running it, and a `-c alias.*`, `-c` value or `GIT_PAGER`/`GIT_EDITOR`/`GIT_SSH_COMMAND` that runs git is denied. Not covered: aliases or functions defined in an earlier command, scripts a command runs, programs that run a quoted command string (`ssh`, `watch '...'`), and anything outside the repo.
- **Destructive git runs only alone from the repo root** (Matt, 12 Nov 2026, option b). The guard does not follow folders. `git reset --hard`, `git checkout -- .`, `git restore .` and `git branch -D` are checked against the repo's state only when each is the whole command: one simple command starting with `git`, with no `-C`, `--git-dir`, `--work-tree`, env assignment or wrapper, not in a subshell, group, substitution or nested shell, with no `;`, `&&`, `||`, `|`, `&`, newline or heredoc, and run from the repo root (symlinks resolved). Any other shape is denied, even in a clean repo, with the route: run it alone from the repo root, and commit or stash first. A probe that cannot read the repo denies too. A shell write is checked in the folder the tool reports unless the script may change folders (`cd`, `pushd`, `popd`, `source`, `eval`, a function, `alias`, `trap`, `shopt`, `CDPATH`/`GIT_DIR`/`GIT_WORK_TREE`, `env -C`, `sudo -D`, `find -execdir`, `git -C`); then a target made of a guard file's names is denied. The earlier rounds tracked `cd`, `-C` and `env -C` folders, and four verify rounds kept finding ways to point that tracking at the wrong repo (the last: `set -e; true || { true; cd clean; }; git reset --hard` and `git -C clean/link/.. reset --hard` through a symlink). That code is gone. **Now blocked that earlier rounds allowed:** `cd sub && git reset --hard` (and `pushd`, `set -e; cd sub; ...`, `(cd sub && ...)`, `bash -ec 'cd sub; ...'`), `git -C sub reset --hard`, `env -C sub git reset --hard`, `sudo -D sub sh -c 'git reset --hard'`, any destructive git chained with another command (`git status && git reset --hard`), `git reset --hard` run from a subfolder, and in a folder in no repo; the same for `git checkout -- .`, `git restore .` and `git branch -D`; and after a folder change, a shell write whose path uses a guard file's name (`.eng`, `guard`, `.claude`, `.codex`, `.cursor`, `config.json`, `settings.json`, `hooks.json` and the other guard file names), so `cd sub && rm config.json` and `cd docs && echo hi > hooks.json` are denied; run the write from the repo root instead. Round 6 adds: `git checkout <branch>` in a chain (it may be a path; `git switch <branch>` works in any shape), and `git restore <path>` or `git checkout -- <path>` over uncommitted changes. Round 7 adds: the branch-moving forms above in any shape but alone at the root, any `git update-ref` (`-d` and `--stdin` only before), `git reset --hard`, `git checkout -f` and `git switch -f` when any untracked file exists, `git checkout <commit> <path>` and `git restore --source` over an untracked file, and `gh pr merge --admin=false` now passes. Round 8 adds: `git branch -D main`, `git branch -f main HEAD` and the other branch-moving forms on the default branch when it holds a commit no other branch has (it vouched for itself before); a branch or ref option given a variable (`git switch -C "$b" main`, `--force-create="$b"`, `git checkout -B "$b"`, `git worktree add -B "$b"`, `--refmap="$m"`); and `git pull --refmap +main:feat`. Round 9 adds: deleting or moving a branch whose tip only a symbolic ref holds (`git symbolic-ref refs/heads/alias refs/heads/gone`, then `git branch -D gone`, or `origin/HEAD` pointing at it), and moving a branch through a symbolic name (`git branch -f alias main` moves `gone`). Now allowed: deleting or moving a branch whose tip another branch holds, such as a feature branch's base (`git branch -D side` when `feature` contains it), and a worktree path given as a variable (`git worktree add "$WT" main`); any other operand made from a variable in those subcommands is still denied.
- **The guard modules are risk:high here.** eng-standard's own `ship.high_risk.paths` gains `lib/guard.mjs`, `lib/guard-hook.mjs` and `lib/guard-setup.mjs`, which decide what the guard blocks in every repo; `test/self-merge.test.mjs` asserts each. `lib/guards.mjs` (the guards/LOG.md check) stays out, as 0.20.6 says.

## 0.16.1 (8 Nov 2026)

**The watchdog counts memory the way the kernel does** (Matt, 9 Nov 2026 AEDT; Core task p5768f79znhdff9fsd6918vwss8hvb7d). A repo's own test suite is no longer killed because eng mis-measured its memory. In PR 51's verdict 1, a shell with no `XDG_RUNTIME_DIR` fell back to the watchdog, and the watchdog killed eng-standard's suite at 2154 MB summed RSS against the 2048 MB default (exit 137). The same suite passed under the same 2 GB limit in a systemd scope.

- **PSS, not summed RSS.** On Linux the watchdog sums each process's PSS (`/proc/<pid>/smaps_rollup`). PSS splits a shared page between the processes that map it, so the node binary and its libraries count once, as the scope's cgroup counts them. Measured on the devbox over one run of `npm ci && eng run test` (1003 polls at 100 ms, up to 63 processes): summed RSS peaked at 2673 MB and was over 2048 MB in 52 polls. Summed PSS peaked at 1219 MB. The cgroup's `memory.current` peaked at 1291 MB. A process whose `smaps_rollup` cannot be read counts at its RSS, which can only overcount. Ownership is unchanged: pid and start time from the kernel, plus the `ENG_BUDGET_UNIT` tag. Messages say `the process tree reached <n> MB PSS`, and the enforcer line says `process-tree PSS poll`.
- **Polling cost.** Reading `smaps_rollup` is a kernel page-table walk. For 50 node processes it takes about 16 ms per read of the whole tree (median over 3×300 reads; 18–24% of one core at 100 ms, almost all system time). PSS is at most RSS, so the watchdog reads `smaps_rollup` only on a poll where summed RSS is over the budget. The stop decision is the same as reading PSS every poll, and the poll stays at 100 ms. In the suite run above, 52 of 1003 polls would read it.
- **macOS** stays on `ps` RSS, which can overcount pages that processes share. A suite of many processes can be stopped there below its real use. Declare a larger `# budget:` or `--budget` there.
- **eng finds the user manager without a login session.** When `XDG_RUNTIME_DIR` is unset, eng uses `/run/user/<uid>` for the probe and for every `systemd-run --user` and `systemctl --user` call. It does so only when that directory is owned by this uid, has mode 0700 and holds a `bus` socket. A command in a scope then inherits `XDG_RUNTIME_DIR` from `systemd-run`. eng does not change its own environment or the watchdog command's environment. `ENG_BUDGET_ENFORCER` keeps its meaning.

## 0.16.0 (8 Nov 2026)

**Checks are chosen and sized up front** (Matt, 8 Nov 2026; incident Core nd7ergzhq2anaav9ynqkqhfcr18hvk84: an ad hoc TLC run with no -Xmx reached 4.19 GB RSS with ~15 agent sessions running, swap hit 100%, and sshd and T3 Connect stopped answering). Anyone can run a repo's checks without a heavy tool locking the machine up. No new command.

- **Tool choice, as suggestions.** `standard/checks.yml` is the suggested-tool catalog for checks. Each entry states its cost (runtime, typical memory and time), when it earns that cost, its weight and a starting budget. Formal checks default to the repo's own runtime (property tests; `statechart` for flows). TLC, Apalache and Alloy are suggested only for concurrency or distributed protocols, as heavy checks. `standard/tools/tlc.sh` is a pinned (tla2tools 1.7.4), SHA-256-checked, bounded TLC runner (-Xmx768m, -workers 1, timeout 120s; under eng the check's budget sets them).
- **Weight and stage.** A check declares `# weight: heavy` in its header (default light). `eng gate` runs light checks everywhere; heavy ones run in CI (`CI` set) or with `eng gate --heavy`. A local run lists a heavy check as `deferred`, never as passed. **A gate that deferred any check exits 3 (incomplete)** and prints which checks it deferred, that what ran passed, and how to run the rest (`eng gate --heavy`, or CI). Exit 0 means every selected check ran and passed, nothing else. So every caller sees an incomplete gate from the exit code alone, whatever its environment: an `eng run --by` record (direct, nested, or with the gate under `env -i`) holds exit 3, and `eng verdict PASS` and `eng verdict check` refuse it like any failing run. CI runs heavy checks, so a passing CI gate still exits 0, and a repo that declares no heavy check never defers. The first line of `eng gate` says which stage runs. Known limit: nothing stops someone from explicitly running an older eng (before 0.16, for example by an absolute path to an old install) against the same commit; that eng has no stages or budgets, and its result is a choice of tool version, not something 0.16 can see.
- **A check is a leaf; a gate inside one cannot hide a deferral** (PR 50, round 4: a check ran `eng gate check:heavy | cat`, the inner gate deferred and exited 3, `cat` exited 0, and the outer gate printed PASS). `eng lint` rule `check-runs-gate` fails a `verification.checks_dir` script that runs `eng gate` (`eng`, `eng.mjs`, `npx eng`, or a variable named for eng). A line that has to, because a fixture repo's gate is what it tests, ends with `# nested gate: <why>`, a trace a reviewer sees; eng-standard's own `gate-runs-checks.sh` does this. At run time, a gate that ends incomplete also signals every enclosing `eng gate` and `eng run --` of the same repository with SIGURG (PR 50, round 5: the earlier marker files could be pointed by a planted symlink at a private directory that eng then emptied, and a marker write that failed with ENOSPC was swallowed, so `gate | cat` passed again). No file, directory or disk space is involved: nothing can fail to be written and eng deletes nothing. It finds those processes by its process ancestry (`/proc/<pid>/stat`; `ps` elsewhere), by the systemd scope name in `/proc/self/cgroup`, and by the watchdog's inherited unit tag, and signals one only if it named itself: a listening `eng gate` or `eng run --` sets its process title to `eng@gate` or `eng@run`, which on Linux replaces its whole `/proc/<pid>/cmdline` and fits even the shortest launch, `node eng gate` (13 bytes; PR 50, round 10: the earlier `eng-listening gate` was cut to `eng-listening`, so that gate missed the notice). eng never guesses from arguments, so an eng path or `gate` handed as data to another program (a supervisor, `node --eval`, `node -`, an option value; PR 50, rounds 7–9) can never make it a recipient; only a process renamed on purpose (`exec -a`) can look like one. Where the title is not in the process table (macOS `ps` may not show it) nothing is signalled, so on macOS the nested notice may not arrive (best effort; lint still blocks the call) (only eng's own options, before `--`, count, so a `--here` that belongs to the command does not hide a run) and its working directory is not in another repository (start time rechecked for ancestors). The git common dir is read from `.git` and `commondir` on disk, not from a `git` the check's PATH may lack (PR 50, round 6: a check whose PATH had no git could not place the enclosing run, so `gate | cat` passed). Only a listener placed in the gate's own repository is signalled. A gate with no repository, or one that cannot read a listener's working directory, signals nothing (PR 50, round 10: `eng run --by x -- eng run test` ended INCOMPLETE after 364 green tests, because `eng run test` runs the suite in bwrap, whose user namespace cannot read the outer run's `/proc/<pid>/cwd`, and fixture repos' deferring gates signalled the outer run they could not place). The notice is best effort; a signal that marks an honest run of another repository incomplete is harm. `eng run --` listens before git makes its worktree, so a gate run by a post-checkout hook that defers also makes the run exit 3. SIGURG is ignored by default, so a process that is not listening is never killed, and a spurious signal can only make a run fail. A signal that arrives while a step runs makes that step `INCOMPLETE` (with `verification.parallel`, every check running at that moment), so the gate exits 3; an enclosing `eng run` turns its command's exit 0 into 3, so the record cannot back a PASS. An enclosing process it found but could not signal gets a loud warning on stderr, and the inner gate still exits 3. A gate in another process tree, or on another repository (a fixture), signals nothing. Known limit: on the watchdog path, an inner gate that both clears its environment and leaves the process tree before it finishes is not found at run time; the lint rule and the systemd scope (the default on Linux with a user manager) cover it. macOS (`/bin/ps` and `/usr/sbin/lsof`, by absolute path) is source-inferred, not run.
- **Budget, the safety net.** A check declares `# budget: memory=768M workers=1 timeout=120s`; missing parts take the default (memory 2048 MB, 2 workers, timeout 1800s; 2 GB stays under one devbox session's ~2.7 GB share, and a check that needs more declares it). `eng gate` enforces it: a transient `systemd-run --user --scope` with MemoryMax, MemorySwapMax=0 and CPUQuota where that works unprivileged, otherwise a timeout plus an RSS watchdog. The budget covers the whole workload, not just the script: in a scope, every process in its cgroup; under the watchdog on Linux, the leader and every descendant, tracked by pid and start time from spawn on, so one stays counted after it detaches, calls setsid, is re-parented to init or runs under `env -i`, plus every process carrying the run's `ENG_BUDGET_UNIT` tag. The one escape left on the watchdog path: a process that clears its environment and whose parent exits within one 100 ms poll, before any poll sees it. The systemd scope, the default on Linux with a user manager, has no such gap. A check's result waits until the last of its processes has gone, with the timeout and memory limit still on, so a detached worker that goes over budget fails the check. On macOS the watchdog sees the process tree only. Each check also gets its tool flags in its own env only: `JAVA_TOOL_OPTIONS=-Xmx<75%> -XX:ActiveProcessorCount=<workers>`, `NODE_OPTIONS=--max-old-space-size=<75%>`, `GRADLE_OPTS=-Dorg.gradle.workers.max=<workers>`, and `ENG_BUDGET_MEMORY_MB`, `ENG_BUDGET_HEAP_MB`, `ENG_BUDGET_WORKERS`, `ENG_BUDGET_TIMEOUT_S` for TLC's `-workers` and the like. A check its budget stops fails, whatever its exit code (a command that traps TERM and exits 0 still fails), and the message names the budget and where to raise it. A header eng cannot read fails the check. SIGINT, SIGTERM or SIGHUP to `eng gate` kills and awaits every running check and its scope, whether or not that gate owns its `ENG_TMP`.
- **One after another, unless the repo opts in.** Checks run in order, as before. `verification.parallel: true` (default false) runs them side by side while their budgets fit the memory free when the gate started (MemAvailable; `ENG_BUDGET_FREE_MB` caps it) and the cores; a check that does not fit waits and says so. One whose budget is more than the free memory is not started and fails, saying so.
- **`eng run -- <cmd>`** runs under the default budget, or `--budget "memory=4G workers=2 timeout=10m"`, and prints the budget and the enforcer. A command its budget stops exits non-zero with the budget named, and a `--by` run records that failure: the record is written once, from the bounded result, after the output pipes drain. When the command exits, what it left running is killed, as before.
- **Tool flags are set once.** Inside an outer budget (`eng run --budget`), a check's `JAVA_TOOL_OPTIONS`, `NODE_OPTIONS` and `GRADLE_OPTS` replace the flags that eng appended there (named by the inherited `ENG_BUDGET_*`) instead of repeating them; the user's own options stay (PR 50, round 10).
- **`eng lint`** rule `heavy-tool-unbounded`: java, tlc, apalache, alloy or gradle called in a `verification.checks_dir` script with no bound (-Xmx, --max-workers, `ENG_BUDGET_*`, or `eng run`) fails. - **Rendered AGENTS.md** gets "Checks are chosen and sized up front": run heavy tools through `eng run --`, declare weight and budget, how stages work, and where the catalog is.
- `ENG_BUDGET_ENFORCER=systemd|watchdog` picks the path; asking for systemd where it does not work fails rather than falling back.

## 0.12.5 (4 Nov 2026)

**A short socket folder per run, and an opt-in private network** (Motus Lead, 4 Nov 2026; Eng Manager Core task p5711dqnz7m50h56b2jg4kaffh8hcmtv). Motus PR470 had 51 tests and its `ephemeral:launch` failing under 0.12.x, for two reasons. First, every `eng ephemeral` run's TMPDIR is about 98 bytes on the devbox, so the unix sockets its tests bind went past the 107-byte cap. Second, the run's bwrap stops a nested bwrap. On a host with `kernel.apparmor_restrict_unprivileged_userns=1` (Ubuntu 24.04), whatever runs under bwrap is confined to AppArmor's `unpriv_bwrap` profile, which denies every capability. So a test that starts its own `bwrap --unshare-net` fails with "No permissions to create new namespace". Neither host AppArmor nor eng's sandbox changes.

- **`ENG_SOCK_DIR`.** Every `eng ephemeral` run (and every `eng gate` step it wraps) gets `ENG_SOCK_DIR=$HOME/.cache/eng/s/<first 8 hex of sha256(ENG_RUN_ID)>`, mode 0700. On the devbox that is 31 bytes (`/home/dev/.cache/eng/s/xxxxxxxx`), whatever the run id; a nested run's folder sits inside its parent's, at 40. Bind unix sockets there. A container's bind mount resolves it at the same path, because the docker daemon sees it on the host, which the run's private `/tmp` is not. eng sets the variable only when the folder is under 60 bytes, in a home this user owns outside `/tmp`, so code that reads it needs a fallback. It is under `$HOME`, not `XDG_CACHE_HOME`, so its length is fixed per user. It is not under `$XDG_RUNTIME_DIR`, which holds the docker socket: devbox-ops' heavy-lane docker proxy (`workspace heavy run`) refuses any bind from there.
- The folder belongs to one run. eng creates it, never reuses it (an existing one is an error), writes the run id to `ENG_SOCK_DIR/.eng-run`, and removes it with the run's round, on a pass, a failure or SIGINT/SIGTERM/SIGHUP. Inside the run's bwrap, `$HOME/.cache/eng/s` is an empty tmpfs with only this run's folder bound back, so a run does not see another run's folder at its path, and `.eng-run` is read-only. Like the rest of enforcement (0.12.2), this guards against accidental cross-run use, not a deliberate one: the same user can still reach another run's folder through `/proc/<pid>/root`. Under `isolation.mode: fail` the folder stays writable, and the run's docker socket lets a container bind it, although the rest of `~/.cache` is read-only. A run killed with SIGKILL leaves its folder; the next `eng ephemeral` run removes it once that run's eng process is gone, as does `eng clean --apply`, which also removes an ownerless one older than `--older-than`.
- **`isolation.network: private`** (default `host`). The run's bwrap also unshares the network namespace. The run has loopback only: a server on the host's 127.0.0.1 is refused, any other address is unreachable (`ENETUNREACH`), and it cannot reach a host server on an abstract-namespace socket either, which closes that limit of enforced isolation (0.12.2). Filesystem sockets still work, so `DOCKER_HOST` (the run's labelling docker socket) and `ENG_SOCK_DIR` keep working. Containers the run starts keep docker's own network. The run gets `ENG_NETWORK_ISOLATED=1`, so a tool that would start its own network sandbox can see the outer one and not nest a second bwrap. eng never passes an inherited `ENG_SOCK_DIR` or `ENG_NETWORK_ISOLATED` on: it sets both itself.
- A run that would get no network namespace (no usable bwrap, or a run folder under `/tmp`) is refused before it starts, in every mode. Like `isolation.mode: fail`, the switch makes the check strict and keeps runs watched when `ephemeral_runs.mode` is off, in `eng ephemeral` and `eng gate`. It adds to `isolation.mode`, and replaces nothing. In warn mode the run can still use this user's other filesystem sockets (the systemd user bus, tmux, agents), and through them the network. `isolation.mode: fail` covers those too.
- `eng` rejects any other `isolation.network` value. The starter config, the README, `docs/project-isolation.md`, the launch contract and the eng-verify skill describe both. Consuming repos see an eng-verify skill diff on their next `eng sync`.

## 0.12.2 (2 Nov 2026)

**Isolation fixes before enforcement** (Matt, 1 Nov 2026: devbox project isolation will be enforced; Core decision nd74kgtnr9qpq1ztyrasyt84518ha76q). A TLA+ model of devbox run isolation (eng-sandbox PR #19) found the holes. The first two items below (what counts as permanent, and `eng clean --containers`) apply in every mode. Everything else is enforcement, which changes nothing in warn mode, the default. Enforcement is `isolation.mode: fail`, which each repo's lead turns on. Threat model: enforcement stops an honest agent from accidentally using or damaging another project's containers, temp files, caches or Convex deployment; it is not a sandbox against deliberate escape, and the hard boundary (rootless Docker or a per-project Unix user or user namespace per run) is a devbox-ops follow-up.

- **One meaning of permanent.** A container is permanent when it has the persist label (`slaytek.persist=true`) or a restart policy other than `no`, as devbox-ops docker-ephemeral already treats it (`permanent()` in `lib/ephemeral.mjs`). `eng ephemeral` used to `docker rm -f` a restart-policy container a run made. It now keeps it. `slaytek.persist=true` counts even in a repo that sets its own `persist_label`, since it is the devbox-wide marker.
- **`eng clean --containers --apply` keeps permanent containers**, a volume with the persist label, and the volumes a permanent container uses. It also keeps a repo volume that a container it does not remove still uses, and drops `-v` for a container whose anonymous volume is marked. It removed every container and volume with the repo label, marked or not.
- **`isolation.mode: fail` enforces isolation in `eng ephemeral`** (CI and `eng gate`), whatever `ephemeral_runs.mode` says. A run with no private `/tmp` is refused. `/dev/shm` is private. `~/.convex` and the cache home are read-only inside the run, except the checkout, the run folder, this repo's eng caches and the pinned download cache, and one of them that appears fails the run. An unlabelled, non-permanent container made during the run fails it, as does a process started in the checkout outside the run's process tree (a tmux server that was already running). Neither is removed or signalled.
- Under enforcement, `ephemeral_runs.mode: off` no longer skips the watched run (in `eng ephemeral` and `eng gate`). The run's docker socket refuses a writable bind mount of `~/.convex` or the cache home, since Docker mounts outside the sandbox. A failed inspect of an unlabelled container makes the run not fully watched, not a pass. A process started under a tmux or screen server older than the run counts as a stray wherever its cwd is, and any change under `~/.convex` (snapshotted before and after) fails the run, whatever made it.
- Under enforcement, the sockets of servers older than the run (this user's filesystem sockets, and the rootful docker socket) are covered inside the run, so it cannot start or write anything outside the sandbox through them. Enforced runs therefore get no ssh-agent, gpg-agent, systemd user bus or existing tmux, with no per-repo allowlist; git over ssh and signing happen outside them (Core decision nd70c9mympghhypt8ca4mkk3t18hazbe). Accepted limits (Core decision nd746n3mew9ek2j7bsdhd586bs8hax9m), with a per-run Unix user or network namespace as the devbox-ops follow-up: abstract-namespace sockets, and another name for a socket (a relative bind path or a hard link), are not covered. A write through a symlink inside `~/.cache` lands at its target and is accepted.
- Under enforcement, the run's docker socket also refuses `exec`, `start`, `cp`, `attach` or `rm` on a container it did not make and any prune, and the raw upstream socket is hidden. A leftover container whose volume labels cannot be read is removed without `-v`. A bind source that does not exist yet is resolved through its symlinked parents, and starting an exec is checked against its container. Connecting a container to a network, or disconnecting it, is refused unless the run made both the network and the container. A container may not mount a server socket outside the run (the daemon's own, any socket hidden from the run, or a folder holding one), read-only or not; the run's own labelling socket can still be mounted. eng's own caches (this repo's, every cache `hygiene.caches` points elsewhere, and the pinned download cache) are created before the run and stay writable, on a fresh runner too. When the run's docker socket cannot look up an object's owner or a volume's mounts (any answer but found or gone), it refuses the request instead of forwarding it. It reads requests as Docker does: a path in another form (percent-encoded, doubled or dotted) is refused, as is a body whose checked field is spelled in another case or holds a non-ASCII key Go would fold (`ſ`, the Kelvin sign), and it forwards exactly the JSON it checked. An attach to a container the run did not make is refused over any method, websocket GET included. Only attach and exec start may upgrade a connection, and only after Docker answers 101 is it piped both ways. A container may not share host or container namespaces (PID, IPC, network, UTS, user, cgroup), run privileged, loosen its security profile, or add a capability outside an allow-list, so BuildKit builds and `network_mode: host` do not run in enforced runs. Images are not guarded: an enforced run can still remove or commit to an image it did not make. The run's docker socket also refuses parent-folder binds, bind-backed volumes and `--volumes-from` that would write protected home state. A `~/.convex` with a symlink in it is refused, and one that grows past the 20000-entry snapshot limit during the run fails it. A run container removed as a leftover keeps an anonymous volume marked `slaytek.persist=true`.
- **New isolation rule `convex-url`.** A service that runs a convex program must set `connect_env = { CONVEX_SELF_HOSTED_URL = "http://127.0.0.1:{port}" }`, so `eng connect` clients reach the backend eng started, not one found by deployment name. With `isolation.mode: fail`, `eng connect` refuses a `.connect.env` that sets that variable when `connect_env` pins it. It warns in warn mode and fails in fail mode, like every rule. The starter `templates/isolation/project.toml` sets it.
- An unnamed compose file already failed `eng isolation check` in fail mode. A test now pins that.

The gate needs an independent PASS for the exact head commit, and GitHub auto-merge merges. **Mode `queue` (optional speed-up):** where the repo has a merge queue, the PASS binds the patch-id of the queued merge_group commit. `eng doctor` detects which mode the repo can run and fails a mismatch.
- **Gate rules.**
  - Gate, auth and billing paths (`merge.auto.second_provider_paths`) need PASSes from two providers other than the authors'.
  - `merge.auto.verifier_logins` binds verdicts to verifier GitHub identities. Unset, they are self-declared, and `eng doctor` says so.
  - An `auto-revert` PR passes only when all of these hold: opened by `github-actions[bot]`, on `auto-revert/<sha12>`, its target is on main, and it is the exact inverse.
- **`eng verdict ... --pr <n>`** posts the verdict comment and, in a repo with `merge.auto`, dispatches `gate.yml`.
- **`eng merge post`** (`merge-post.yml`): the shipped-artifact check after each merge. A failure opens an auto-revert PR with auto-merge on and dispatches the check with the PR number.
- **`eng merge watch`** (`merge-watch.yml`, every 10 min):
  - A red or missing check with no activity for 30 min gets the `stuck` label.
  - A FAIL restarts the owner at once. A missing verdict, or a missing second-provider PASS, restarts it 30 min after the push. A failed webhook delivery is retried.
  - In strict mode it updates a behind PR that has auto-merge on.
- **`eng merge settings`** prints the ruleset for the declared mode and never applies it.
- **Reference workflows and config** in `templates/merge-auto/` (`gate.yml`, `merge-post.yml`, `merge-watch.yml`, `ci.yml`, `eng.config.yml`), copied into a consuming repo's `.github/workflows/`. They are not live in eng-standard.
