# Changelog

Versions follow the commit titles on `main` (`vX.Y.Z: ...`). Minor = new command, config or policy area; patch = rule or doc addition to an existing area. History before 0.7.1 is in `git log`.

## 0.18.2 (10 Nov 2026)

**Repos may lower merge gates, never silently** (Matt, 10 Nov 2026). A repo may lower any merge-gate level, even in the PR that changes it, and eng does not block it. The risk is an unnoticed loosening, so eng makes each one visible instead.

- **Gate settings are risk:high in the template.** `ship.high_risk.paths` in `templates/eng.config.yml` adds `eng.config.yml` and `.eng/checks/**`, and `reasons` adds `gate settings`. A PR that changes, adds, removes or renames either is risk:high (`lib/risk.mjs`), so it needs the repo owner. Only new repos get this; an existing config keeps its paths, and doctor lists the two as missing. A PR may also drop these paths in the same change; doctor then lists `ship.high_risk.paths` as below default.
- **A change to `ship.high_risk` itself is risk:high in every repo.** When `eng.config.yml` changes, `classifyRisk` (`lib/risk.mjs`) compares the `ship.high_risk` block at the base and the head. Any difference (a path removed or added, the verifier count, the label, the block removed) adds the hit `ship.high_risk`, whatever the head's paths say. So a PR that drops `eng.config.yml` from its own paths still needs `ship.high_risk.verifiers` verifiers. The comparison only detects the change; the head's levels apply, and nothing blocks the merge beyond the risk:high rule. `eng verdict check`, the risk label and self-merge (`scripts/pr-gate.mjs`) all use it, and `eng verdict check` prints `ship.high_risk changed in this change`.
- **`eng doctor` lists gates below the standard default.** One section, "Gates below the standard default": the setting, the repo's value, the standard default (the template's value, else the code's fallback) and the line that restores it. A repo at or above every default prints one line saying so. The section never changes doctor's exit code. The settings, one table in `lib/gate-levels.mjs`: `renovation.gates.mode` (warn), `gates.required` (a template gate removed), `ship.high_risk.verifiers`, `ship.high_risk.paths` (a template path missing), `merge.auto.high_risk_verifiers` and `merge.auto.tests_check` (when `merge.auto` is set), `verification.flake_runs`, `verification.review_only_paths` (a path added), `verification.checks_dir` (moved), `db.additive_only` (false), `e2e.flake_runs`, `e2e.policy.unmatched` (skip), `e2e.policy.labels` and each `e2e.policy.run_on` list (an entry missing) and each `e2e.policy.skip_on` list (an entry added), unless `e2e.policy.mode` is always, the `hygiene.disk_rules` modes of `tests_leave_nothing`, `no_cache_in_evidence` and `evidence_budget`, `hygiene.disk_rules.evidence_budget.max_mb` (raised), `hygiene.run_rules.ephemeral_runs.mode`, `hygiene.tmp_lint` and `hygiene.disk_lint` (false), `laws.enabled` (false or removed), `flags.file` (null, removed or moved) and `hygiene.disk_rules.no_cache_in_evidence.markers` (a template marker missing).
- **Every other gate setting that differs is listed too.** A second doctor section, "Other gate settings changed from the standard (direction not judged)", lists each other setting the repo sets under `gates`, `renovation.gates`, `verification`, `ship`, `merge`, `hygiene`, `laws`, `flags`, `db`, `e2e` or `constraints` to a value other than the standard, with both values. The standard is the template for the repo's profile (under `profile: slaytek` the slaytek persist markers are the default), plus `merge.auto`'s code defaults when the repo sets `merge.auto`. A key the repo leaves out is not listed. A fresh `eng init` config lists nothing in either section, and neither section changes doctor's exit code.
- **Doctor no longer fails a supported lowering.** `mode: off` on a disk rule or on `ephemeral_runs`, and `hygiene.tmp_lint: false` or `hygiene.disk_lint: false`, used to fail doctor. They are now rows in the section above. Doctor's own lint scan follows the repo's `tmp_lint` and `disk_lint`. An invalid value (a mode that is not fail, warn or off) is still a config error.
- **Gates read the PR's own config.** The rendered Buildkite pipeline runs `npx eng lint`, not `npx eng lint --config-from origin/<default branch>`, so `renovation.gates.mode: warn` in a PR applies to that PR. `eng lint --config-from` is gone; a stale pipeline that still passes it gets a note and lints on the checkout's own config. `eng merge gate` reads `merge.auto` from the PR head's (or queued commit's) `eng.config.yml`, and `--config-from` is gone there too; `templates/merge-auto/ci.yml` no longer passes `--config-from origin/main`. One value stays with the trusted checkout: `merge.auto.check`, the required check's name. With the PR's name, a PR job carrying the real name would no longer count as forged. That is about the check's identity, not a gate level.
- **Not listed, and why.** `gates.skipped_is_failed: false` is already a config error. `renovation.merge_policy.strict: false` is the standard; `true` is the stricter divergence. `hygiene.disk_rules.pinned_downloads.mode` has no built-in check, so it gates nothing. `e2e.policy.mode: always` is stricter than the standard. `merge.auto.verifier_logins` unset is already a doctor failure. `merge.auto.high_risk_paths` has no standard list (the template sets no `merge.auto`), and an empty list is a config error.
- **Not built, by decision.** No block on lowering, no rule that a lowered level takes effect only after a merge under the old level, and no gate that reads config from the base branch.
- **Slaytek repos see exactly one rendered line change.** Under `profile: slaytek`, `.eng/ci/pipeline.yml`'s lint step goes from `command: "npx eng lint --config-from origin/main"` to `command: "npx eng lint"`, and every other file is byte-identical to v0.17.2. `test/profile.test.mjs` compares every rendered file with `test/fixtures/profile/v0.18.2.json` and checks that putting the old line back gives the v0.17.2 bytes.
- **Upgrade:** zero manual edits. Doctor may now list gates below default and other changed gate settings; to match the standard, apply the restore lines it prints, including the two new `ship.high_risk.paths`. Run `eng sync` to drop `--config-from` from the rendered pipeline. A repo on `templates/merge-auto/` copies the new `ci.yml` line.

## 0.18.1 (10 Nov 2026)

**Two gate fixes from an independent sweep.**

- **eng scans `.claude/skills` and `.claude/agents` again.** v0.17.2 had dropped both folders from every repo scan, not only from what eng writes. So `eng lint` and the secret-filename check missed tracked files there: an `id_rsa` in `.claude/skills/` got no finding. 0.18.1 restores the scans: lint rules, the secret-filename check and baselines, `eng doctor`'s toolchain checks, `rules prove` and the e2e check see files in those folders again, matched ignoring case (`.Claude/Skills` too). The secret-filename check needs names only, so it sees every path there. Scans that read contents read a path there only when it is a readable regular file: a link is not followed, and an unreadable file or a FIFO is skipped, so it cannot crash, block or fail doctor, lint or gate. eng still never writes there: the render refusal, the prune exclusion, the `skills_dir` and `checks_dir` config errors and the empty-folder skip are unchanged.
- **`eng verdict check` counts distinct verifiers on risk:high.** Before, it passed on one counted PASS for any change, so `eng verdict status` posted `verdict` success after the first verifier even on a risk:high PR, and only self-merge enforced the count. Now, when a changed path (or a rename's old path) matches `ship.high_risk.paths`, the check needs counted PASSes on the exact head from `ship.high_risk.verifiers` (default 2) distinct `--by` verifiers, the same rule as self-merge and the same classifier as the risk label (`lib/risk.mjs`, with `version_only` bumps kept low). With fewer it fails with `risk:high needs 2 distinct verifiers on <sha>; have 1 (<by>)`, and that line is the status description. Each verifier's latest verdict counts and any FAIL blocks, as before. `eng verdict status --pr <n>` (and `eng verdict ... --pr <n>`) counts this clone's records together with the PR's `eng-verdict/v1` comments for the exact head, read through self-merge's own rules (`parseVerdicts`, `trusted` with `verifier_logins`, `passProblem`, latest per verifier, any FAIL blocks). git notes do not travel with fetch or clone, so two verifiers in separate clones each hold only their own record: the PR comments are what lets the second one post success. `eng verdict check --pr <n>` does the same. Plain `eng verdict check` stays local-only: a lone clone counts only the verdicts recorded in its own notes, so on risk:high it reports `have 1` until the other verifiers' verdicts are on the PR and the check reads them with `--pr`. A config with no `ship.high_risk` block, or no path that matches, behaves as before. **Upgrade:** a repo whose config sets `ship.high_risk.paths` now needs that many verifiers before its `verdict` status turns green on a risk:high change.

## 0.17.2 (9 Nov 2026)

**eng stops writing into harness skill folders** (Matt, 9 Nov 2026: "this sounds much smoother"; Core nd70ke343v7gc0eakdejg7m5f18hx1p9, Direction change). The five review rounds of PR #58 all came from eng managing per-skill links inside `.claude/skills` and `.claude/agents`, folders that developers and other tools also own. This release removes that work instead of hardening it. No new command and no config change.

- **eng never creates, changes or deletes anything in `.claude/skills` or `.claude/agents`.** `eng sync`, `eng sync --check`, `eng init` and `eng doctor` only stat them for the visibility report below, whatever they are: real folders, symlinks into or out of the repo, loops, dangling links, unreadable entries or FIFOs. eng's repo scans (`eng doctor`'s toolchain checks, `eng lint`, lint and secret-filename baselines, `rules prove`) skip both folders, so a file there is never opened, an unreadable file or FIFO there cannot fail or block them, and lint no longer reports findings in a developer's files there. Skills still render into `agents.skills_dir` (`.agents/skills`) and subagents into the folder beside it (`.agents/agents`), byte for byte as in 0.17.1. Every other file eng renders, `.claude/settings.json` included, is unchanged.
- **No setting can point eng into them.** A folder eng writes into that lands in `.claude/skills` or `.claude/agents` is a config error: `agents.skills_dir`, the subagent folder beside it (so `.claude/custom` is refused, its subagents would go to `.claude/agents`) and `verification.checks_dir`. Each is resolved against the repo root before it is compared, ignoring case, so `./.Claude/Skills` and `../<repo>/.claude/skills` count too, and every file eng is about to render is checked the same way. Every command that reads the config refuses it (`eng sync`, `sync --check`, `init`, `doctor`) before it reads, creates or writes anything, and sync does not migrate a refused config. Before, sync rendered there over a developer's files, and a FIFO there blocked sync. `.claude/foo/skills` is fine. With `agents.skills_dir: .claude` (their parent), sync's empty-folder cleanup skips `.claude/skills` and `.claude/agents`, and an unreadable folder is skipped, not a crash. A file an older lock lists in those folders, by any path, is never pruned: it is the developer's now.
- **The 0.17.1 refusal is gone.** A symlinked `.claude`, `.claude/skills` or `.claude/agents` is no longer a config error: with nothing to write there, there is nothing to refuse. `.claude/skills -> ../.agents/skills` is now the simplest layout.
- **`eng sync --check` no longer checks links.** A missing or different link in `.claude/skills` is not drift.
- **Visibility report.** With `claude-code` in `agents.harnesses`, `eng sync` and `eng doctor` print one line: `ok` when every eng skill is at `.claude/skills/<name>/SKILL.md` and every subagent at `.claude/agents/<file>`, else a `WARN` with the count and the one-step fix. A path counts only when it stats as a readable regular file; eng never opens it, so a FIFO cannot block it, and an error counts as not visible. A skill selected twice counts once. The fix is `ln -s ../.agents/skills .claude/skills` (and `ln -s ../.agents/agents .claude/agents`) when the folder does not exist, otherwise "add the missing entries, or point it at `.agents/skills`". The link target is relative to the real `.claude` folder, so it works when `.claude` is itself a link (and is `.` when the skills folder is `.claude` itself), and a path with spaces or quotes is shell-quoted. It is a warning: doctor never fails on it and `--check` never reads it. The rendered `AGENTS.md` already tells agents to read `.agents/skills/<name>/SKILL.md` directly, so this matters only for Claude Code's own skill discovery.
- **The lock stops recording `links`.** `.eng/lock.json` lists `package` and `files` only. A 0.17.1 lock with `links` reads fine, and the next `eng sync` rewrites it without them.
- **Upgrade:** zero manual edits, and no config migration (no key changes), unless `agents.skills_dir` or `verification.checks_dir` points into `.claude/skills` or `.claude/agents`: then sync names it, and you move it (the defaults are `.agents/skills` and `.eng/checks`). Move the pin, run `eng sync` (the lock loses `links`), commit. The per-skill links an earlier eng made in `.claude/skills` and `.claude/agents` stay exactly as they are, and Claude Code keeps seeing those skills. eng no longer prunes or repairs them, so a skill added later is not linked: the doctor line says so, and `ln -s ../.agents/skills .claude/skills` in place of the per-skill folder (after removing it yourself) covers every future skill.

## 0.17.1 (9 Nov 2026)

**Adoption fixes from Kalsigns** (Core nd7cpb3k1atph5xsgdfzt4nm4d8ht44g: the Kalsigns adoption of v0.16 hit five gaps the next adopter would hit too). No new command and no config change.

- **A repo's own PR template stays the only one.** GitHub reads a PR template from `.github/`, the root or `docs/`, named in any case, as a file or a `PULL_REQUEST_TEMPLATE/` folder. When the repo has one that eng did not render, `eng sync` renders no `.github/pull_request_template.md` and does not touch theirs; `eng doctor` prints which template is in use. Before, eng wrote its own beside `.github/PULL_REQUEST_TEMPLATE.md` (two templates on Linux; on a case-insensitive disk, eng's bytes over theirs). A repo whose only template is eng's keeps it, unchanged. Pruning a file eng no longer renders now needs its exact name on disk, so a name that differs only in case is never removed.
- **A check can bind a unix socket in its TMPDIR.** Each gate step's TMPDIR was a folder inside ENG_TMP, under the scratch root, with the repo name twice: 123 bytes for Kalsigns' `check-quote-versions-tla` under the default scratch root, 143 with `/tsx-1000/12345.pipe`, past the 107-byte socket limit (103 on macOS), so tsx's IPC pipe failed with EINVAL. Each step's TMPDIR is now a fresh 0700 folder in the gate's own socket folder (`$HOME/.cache/eng/s/<8 hex>/<6>`, 38 bytes for a `/home/dev` home; inside an `eng run <name>`, in that run's folder). It is removed on exit, and the next gate or run reaps it if the gate was killed. With no usable home it stays inside ENG_TMP, as before. `$TMPDIR/tsx-1000/12345.pipe` and a 40-character socket name both bind, through `eng gate` and `eng run -- eng gate`, under the systemd scope and the watchdog. The TMPDIR of `eng run -- <cmd>` itself is unchanged.
- **A failing step's reason is a failing line, and the gate prints the end of its output.** The reason was the first output line matching `failed`, so `ok 1 - reports failed uploads` could be it. It is now the first line that signals a failure (TAP `not ok`, node `✖`, vitest `×`, `FAIL`, `Error:`, an `N failed` summary), never a line that marks a pass (`ok`, `✔`, `✓`, `PASS`), else the last line. Terminal colour and control sequences are stripped before a line is classified, so a coloured `✓` line is a pass. When a step's final result is a failure (a check that exits 0 but leaves files in its TMPDIR included), the gate prints to stderr the end of its output, colours kept: at most 40 lines and 8 KiB, under `eng gate: <step> failed; the end of its output`. Output is read as it streams, so a step that prints gigabytes is neither killed nor cut short (before, a gate command over 1 MiB of output was killed with SIGTERM and the gate exited 143). eng keeps no copy of the output: no file is written.
- **`eng sync` refuses a symlinked `.claude/skills`.** When `.claude`, `.claude/skills` or `.claude/agents` is a symlink, sync and `sync --check` fail with a config error naming the path and the fix (make it a real directory), and sync writes nothing. Before, sync wrote a link per skill through it: with `.claude/skills -> ../.agents/skills`, each link replaced the skill it pointed to.
- **A check's container needs docker's own limits.** `docker run` and `podman run` start the container in the daemon's cgroup, outside the check's budget scope and the watchdog's process tree, and no `ENG_BUDGET_UNIT` reaches it (Kalsigns review r2: TLC with only `-Xmx1g` inside). `eng lint` and `eng doctor` now warn (`container-unbounded`, a new rule id) on a check script's `docker run` or `podman run` whose own options lack a positive `--memory` (or `-m`) or `--cpus` (`.5` and `1.25` count). It is a warning, never a failure of lint, the gate or doctor: a text check of common shell forms cannot parse shell, and a false positive that blocks a valid repo costs more than a missed odd form. Each invocation is read on its own, across backslash-continued lines and inside `$(...)`: options are the words between `run` and the image, read in order so the last value wins (`--memory=128m -m0` is unbounded; `0` means no limit to docker), so a flag after the image, in a comment or on another command on the line does not count. Redirections (`2>/dev/null`, `>f 2>&1`, `&>f`, `< f`) are not options, and a heredoc body is text, not a command. `-Xmx` and `eng run --` do not count, since neither bounds the container. It is a text check of common forms in one script: a wrapper function, a variable or an unusual construction can hide an invocation from it. `heavy-tool-unbounded` is unchanged and still fails an unbounded JVM. The pattern is in `standard/checks.yml` (`containers`) and the rendered budget rules: `--memory` and `--cpus` within the check's budget, `--memory-swap` equal to `--memory`, `--rm`, `--name "$ENG_BUDGET_UNIT"` (the id eng gives each check run), and `trap 'docker rm -f "$ENG_BUDGET_UNIT"' EXIT`. docker enforces those limits; eng does not. The trap runs when the check exits on its own; when eng stops a check (a budget timeout or memory stop, a cancelled gate), eng does not promise it runs (PR #57 verdict 3: under the systemd scope a timeout ended the shell before its trap), so `docker rm -f <name>` removes what is left. eng removes no container.
- **Upgrade:** zero manual edits, and no config migration (no key changes). Move the pin, run `eng sync` (AGENTS.md gains the container rule; a repo with its own PR template loses eng's copy), commit. Every check that ran before still runs. A check script with an unbounded `docker run` now gets a `container-unbounded` warning from `eng lint` and `eng doctor`; nothing fails on it. Add the flags.

## 0.17.0 (9 Nov 2026)

**Repos extend the pre-push hook** (decision Core nd7cpb3k1atph5xsgdfzt4nm4d8ht44g, 9 Nov 2026, on the Kalsigns escalation). Adopting eng replaced Kalsigns' own `.githooks/pre-push`, which refuses new refs and fast-forwards to `main`, `sandbox/john` and `dev`. After adoption eng's hook ran alone, and Kalsigns review refused 0 of 12 protected pushes. `core.hooksPath` is shared by every worktree of a clone, so moving it is no fix.

- **`hooks.pre_push: [<command>, ...]`**, beside `hooks.pre_commit`. `.githooks/pre-push` keeps git's ref lines from stdin in memory (no temp file, so an interrupted push leaves nothing behind; a failed, partial or interrupted read fails the push) and runs eng's push checks on them first, unchanged. When they refuse, the push fails and no command runs. Then each command runs in order, in its own `sh -c`, with the hook's arguments as `$1` (remote name) and `$2` (URL) and the same stdin bytes, an empty stdin included. The first command that fails stops the push: the hook prints `eng: hooks.pre_push command <i> of <n> failed (exit <code>): <command>` and exits with that code. A command can refuse more pushes; it cannot let through one that eng refuses. `eng doctor` warns when a `hooks.pre_push` command runs a repo script without passing the hook's arguments on (`scripts/x.sh` instead of `scripts/x.sh "$@"`), because such a script sees no remote name or URL.
- **Validation.** `hooks.pre_push`, like `hooks.pre_commit`, must be a list of non-empty commands; anything else is a config error naming the key.
- **`eng doctor`** fails a `hooks.pre_commit` or `hooks.pre_push` command whose first word is a repo-relative path (`scripts/x.sh`, `./bin/check`) that is missing or not executable. This is new for `pre_commit` too, which had no doctor check.
- **`git push --no-verify`** skips the whole hook, eng's checks and the repo's commands alike. That is git's behaviour and eng does not change it; the Claude Code deny list blocks the common forms for agents, and a server ruleset is the real wall for protected branches. `docs/lifecycle.md` (Git hooks) says so.
- The template gains `pre_push: []`. No migration: the key is new and optional, and nothing is retired.
- **Upgrade:** zero manual edits. Move the pin and run `eng sync`. Without `hooks.pre_push`, or with `[]`, `.githooks/pre-push` renders byte for byte as in 0.16.2 (`test/pre-push.test.mjs`). A repo with its own pre-push rules moves them into a script and lists it, for example `pre_push: ['scripts/git-hooks/branch-classes.sh "$@"']`.

## 0.16.2 (8 Nov 2026)

**Help never runs a command, and coverage claims are true per harness** (R3b, 8 Nov 2026: a Codex agent onboarded a Python repo from the docs alone and hit four defects that hurt every new adopter). No new command and no config change.

- **Help is inert.** `eng <command> --help` and `-h` (or `help <command>` as the first argument) print that command's usage and exit 0, for all ten commands and their subcommands. They write no file, install no hook, run no check, start nothing and read no network. Before, `eng init --help` seeded the config, ran sync and set `core.hooksPath`, and `eng run --help` looked for a project command named `--help`. Only eng's own options count: a `--help` after `--` belongs to the command eng runs. Help for an unknown command exits 1.
- **Coverage claims name the harness.** Only Claude Code gets an executable agent deny list (`.claude/settings.json`) and the post-edit hook. The rendered AGENTS.md rule table, SHIPPING.md rule 1 and the Branches section now name "the Claude Code deny list" only when `claude-code` is in `agents.harnesses`, and name each other harness as having none (for example `codex: no agent deny list`). Before, every repo read "agent deny lists only", Codex-only repos included.
- **`eng doctor`** prints one line per selected harness: what Claude Code gets, and for every other harness the protections it does not get (`codex: no agent deny list; --no-verify and --admin are guarded by this text only ...`). It is a warning, not a failure.
- **Tool detection counts the product.** Doctor's toolchain detection (`hygiene.caches.bun`, cargo, deno, vite) ignores the files eng renders (installed skills, such as pstack's `poteto-mode/scripts/bun.lock`) and the eng package when it sits inside the repo. A Python repo with eng's skills no longer needs a Bun cache; a repo with its own `bun.lock` still does.
- **A reduced config fails with a message.** `eng sync` (and `sync --check`, `init`) checks every shape it renders from before rendering, and names each missing key with the template's default (`stack.frameworks is missing: ... The template default is stack.frameworks: {"allowed":[...]}`). Before, a config without `stack.frameworks` died with `TypeError: Cannot read properties of undefined`. Two reads that had a default elsewhere now use it: `e2e.evidence_dir` (`.eng/evidence`) and `verification.checks_dir` (`.eng/checks`).

## 0.16.1 (8 Nov 2026)

**The watchdog counts memory the way the kernel does** (Matt, 9 Nov 2026 AEDT; Core task p5768f79znhdff9fsd6918vwss8hvb7d). A repo's own test suite is no longer killed because eng mis-measured its memory. In PR 51's verdict 1, a shell with no `XDG_RUNTIME_DIR` fell back to the watchdog, and the watchdog killed eng-standard's suite at 2154 MB summed RSS against the 2048 MB default (exit 137). The same suite passed under the same 2 GB limit in a systemd scope.

- **PSS, not summed RSS.** On Linux the watchdog sums each process's PSS (`/proc/<pid>/smaps_rollup`). PSS splits a shared page between the processes that map it, so the node binary and its libraries count once, as the scope's cgroup counts them. Measured on the devbox over one run of `npm ci && eng run test` (1003 polls at 100 ms, up to 63 processes): summed RSS peaked at 2673 MB and was over 2048 MB in 52 polls. Summed PSS peaked at 1219 MB. The cgroup's `memory.current` peaked at 1291 MB. A process whose `smaps_rollup` cannot be read counts at its RSS, which can only overcount. Ownership is unchanged: pid and start time from the kernel, plus the `ENG_BUDGET_UNIT` tag. Messages say `the process tree reached <n> MB PSS`, and the enforcer line says `process-tree PSS poll`.
- **Polling cost.** Reading `smaps_rollup` is a kernel page-table walk. For 50 node processes it takes about 16 ms per read of the whole tree (median over 3×300 reads; 18–24% of one core at 100 ms, almost all system time). PSS is at most RSS, so the watchdog reads `smaps_rollup` only on a poll where summed RSS is over the budget. The stop decision is the same as reading PSS every poll, and the poll stays at 100 ms. In the suite run above, 52 of 1003 polls would read it.
- **macOS** stays on `ps` RSS, which can overcount pages that processes share. A suite of many processes can be stopped there below its real use. Declare a larger `# budget:` or `--budget` there.
- **eng finds the user manager without a login session.** When `XDG_RUNTIME_DIR` is unset, eng uses `/run/user/<uid>` for the probe and for every `systemd-run --user` and `systemctl --user` call. It does so only when that directory is owned by this uid, has mode 0700 and holds a `bus` socket. A command in a scope then inherits `XDG_RUNTIME_DIR` from `systemd-run`. eng does not change its own environment or the watchdog command's environment. `ENG_BUDGET_ENFORCER` keeps its meaning.
- **Upgrade:** zero manual edits. Move the pin. Nothing renders differently. A suite that the watchdog stopped for summed RSS now runs to its result.

## 0.16.0 (8 Nov 2026)

**Checks are chosen and sized up front** (Matt, 8 Nov 2026; incident Core nd7ergzhq2anaav9ynqkqhfcr18hvk84: an ad hoc TLC run with no -Xmx reached 4.19 GB RSS with ~15 agent sessions running, swap hit 100%, and sshd and T3 Connect stopped answering). Anyone can run a repo's checks without a heavy tool locking the machine up. No new command.

- **Tool choice, as suggestions.** `standard/checks.yml` is the suggested-tool catalog for checks. Each entry states its cost (runtime, typical memory and time), when it earns that cost, its weight and a starting budget. Formal checks default to the repo's own runtime (property tests; `statechart` for flows). TLC, Apalache and Alloy are suggested only for concurrency or distributed protocols, as heavy checks. `standard/tools/tlc.sh` is a pinned (tla2tools 1.7.4), SHA-256-checked, bounded TLC runner (-Xmx768m, -workers 1, timeout 120s; under eng the check's budget sets them).
- **Weight and stage.** A check declares `# weight: heavy` in its header (default light). `eng gate` runs light checks everywhere; heavy ones run in CI (`CI` set) or with `eng gate --heavy`. A local run lists a heavy check as `deferred`, never as passed. **A gate that deferred any check exits 3 (incomplete)** and prints which checks it deferred, that what ran passed, and how to run the rest (`eng gate --heavy`, or CI). Exit 0 means every selected check ran and passed, nothing else. So every caller sees an incomplete gate from the exit code alone, whatever its environment: an `eng run --by` record (direct, nested, or with the gate under `env -i`) holds exit 3, and `eng verdict PASS` and `eng verdict check` refuse it like any failing run. CI runs heavy checks, so a passing CI gate still exits 0, and a repo that declares no heavy check never defers. The first line of `eng gate` says which stage runs. Known limit: nothing stops someone from explicitly running an older eng (before 0.16, for example by an absolute path to an old install) against the same commit; that eng has no stages or budgets, and its result is a choice of tool version, not something 0.16 can see.
- **A check is a leaf; a gate inside one cannot hide a deferral** (PR 50, round 4: a check ran `eng gate check:heavy | cat`, the inner gate deferred and exited 3, `cat` exited 0, and the outer gate printed PASS). `eng lint` rule `check-runs-gate` fails a `verification.checks_dir` script that runs `eng gate` (`eng`, `eng.mjs`, `npx eng`, or a variable named for eng). A line that has to, because a fixture repo's gate is what it tests, ends with `# nested gate: <why>`, a trace a reviewer sees; eng-standard's own `gate-runs-checks.sh` does this. At run time, a gate that ends incomplete also signals every enclosing `eng gate` and `eng run --` of the same repository with SIGURG (PR 50, round 5: the earlier marker files could be pointed by a planted symlink at a private directory that eng then emptied, and a marker write that failed with ENOSPC was swallowed, so `gate | cat` passed again). No file, directory or disk space is involved: nothing can fail to be written and eng deletes nothing. It finds those processes by its process ancestry (`/proc/<pid>/stat`; `ps` elsewhere), by the systemd scope name in `/proc/self/cgroup`, and by the watchdog's inherited unit tag, and signals one only if it named itself: a listening `eng gate` or `eng run --` sets its process title to `eng@gate` or `eng@run`, which on Linux replaces its whole `/proc/<pid>/cmdline` and fits even the shortest launch, `node eng gate` (13 bytes; PR 50, round 10: the earlier `eng-listening gate` was cut to `eng-listening`, so that gate missed the notice). eng never guesses from arguments, so an eng path or `gate` handed as data to another program (a supervisor, `node --eval`, `node -`, an option value; PR 50, rounds 7–9) can never make it a recipient; only a process renamed on purpose (`exec -a`) can look like one. Where the title is not in the process table (macOS `ps` may not show it) nothing is signalled, so on macOS the nested notice may not arrive (best effort; lint still blocks the call) (only eng's own options, before `--`, count, so a `--here` that belongs to the command does not hide a run) and its working directory is not in another repository (start time rechecked for ancestors). The git common dir is read from `.git` and `commondir` on disk, not from a `git` the check's PATH may lack (PR 50, round 6: a check whose PATH had no git could not place the enclosing run, so `gate | cat` passed). Only a listener placed in the gate's own repository is signalled. A gate with no repository, or one that cannot read a listener's working directory, signals nothing (PR 50, round 10: `eng run --by x -- eng run test` ended INCOMPLETE after 364 green tests, because `eng run test` runs the suite in bwrap, whose user namespace cannot read the outer run's `/proc/<pid>/cwd`, and fixture repos' deferring gates signalled the outer run they could not place). The notice is best effort; a signal that marks an honest run of another repository incomplete is harm. `eng run --` listens before git makes its worktree, so a gate run by a post-checkout hook that defers also makes the run exit 3. SIGURG is ignored by default, so a process that is not listening is never killed, and a spurious signal can only make a run fail. A signal that arrives while a step runs makes that step `INCOMPLETE` (with `verification.parallel`, every check running at that moment), so the gate exits 3; an enclosing `eng run` turns its command's exit 0 into 3, so the record cannot back a PASS. An enclosing process it found but could not signal gets a loud warning on stderr, and the inner gate still exits 3. A gate in another process tree, or on another repository (a fixture), signals nothing. Known limit: on the watchdog path, an inner gate that both clears its environment and leaves the process tree before it finishes is not found at run time; the lint rule and the systemd scope (the default on Linux with a user manager) cover it. macOS (`/bin/ps` and `/usr/sbin/lsof`, by absolute path) is source-inferred, not run.
- **Budget, the safety net.** A check declares `# budget: memory=768M workers=1 timeout=120s`; missing parts take the default (memory 2048 MB, 2 workers, timeout 1800s; 2 GB stays under one devbox session's ~2.7 GB share, and a check that needs more declares it). `eng gate` enforces it: a transient `systemd-run --user --scope` with MemoryMax, MemorySwapMax=0 and CPUQuota where that works unprivileged, otherwise a timeout plus an RSS watchdog. The budget covers the whole workload, not just the script: in a scope, every process in its cgroup; under the watchdog on Linux, the leader and every descendant, tracked by pid and start time from spawn on, so one stays counted after it detaches, calls setsid, is re-parented to init or runs under `env -i`, plus every process carrying the run's `ENG_BUDGET_UNIT` tag. The one escape left on the watchdog path: a process that clears its environment and whose parent exits within one 100 ms poll, before any poll sees it. The systemd scope, the default on Linux with a user manager, has no such gap. A check's result waits until the last of its processes has gone, with the timeout and memory limit still on, so a detached worker that goes over budget fails the check. On macOS the watchdog sees the process tree only. Each check also gets its tool flags in its own env only: `JAVA_TOOL_OPTIONS=-Xmx<75%> -XX:ActiveProcessorCount=<workers>`, `NODE_OPTIONS=--max-old-space-size=<75%>`, `GRADLE_OPTS=-Dorg.gradle.workers.max=<workers>`, and `ENG_BUDGET_MEMORY_MB`, `ENG_BUDGET_HEAP_MB`, `ENG_BUDGET_WORKERS`, `ENG_BUDGET_TIMEOUT_S` for TLC's `-workers` and the like. A check its budget stops fails, whatever its exit code (a command that traps TERM and exits 0 still fails), and the message names the budget and where to raise it. A header eng cannot read fails the check. SIGINT, SIGTERM or SIGHUP to `eng gate` kills and awaits every running check and its scope, whether or not that gate owns its `ENG_TMP`.
- **One after another, unless the repo opts in.** Checks run in order, as before. `verification.parallel: true` (default false) runs them side by side while their budgets fit the memory free when the gate started (MemAvailable; `ENG_BUDGET_FREE_MB` caps it) and the cores; a check that does not fit waits and says so. One whose budget is more than the free memory is not started and fails, saying so.
- **`eng run -- <cmd>`** runs under the default budget, or `--budget "memory=4G workers=2 timeout=10m"`, and prints the budget and the enforcer. A command its budget stops exits non-zero with the budget named, and a `--by` run records that failure: the record is written once, from the bounded result, after the output pipes drain. When the command exits, what it left running is killed, as before.
- **Tool flags are set once.** Inside an outer budget (`eng run --budget`), a check's `JAVA_TOOL_OPTIONS`, `NODE_OPTIONS` and `GRADLE_OPTS` replace the flags that eng appended there (named by the inherited `ENG_BUDGET_*`) instead of repeating them; the user's own options stay (PR 50, round 10).
- **`eng lint`** rule `heavy-tool-unbounded`: java, tlc, apalache, alloy or gradle called in a `verification.checks_dir` script with no bound (-Xmx, --max-workers, `ENG_BUDGET_*`, or `eng run`) fails. A bound set earlier in the same script counts: `export JAVA_TOOL_OPTIONS=-Xmx768m` (or `JDK_JAVA_OPTIONS`, `_JAVA_OPTIONS`) before `java`; `JAVA_OPTS` or `JVM_ARGS` only for a call that passes them or a wrapper that reads them (gradle; apalache-mc), since java itself ignores them; `GRADLE_OPTS=-Dorg.gradle.workers.max=<n>` before gradle. `eng rules prove` bites it on the incident's shape.
- **Rendered AGENTS.md** gets "Checks are chosen and sized up front": run heavy tools through `eng run --`, declare weight and budget, how stages work, and where the catalog is.
- `ENG_BUDGET_ENFORCER=systemd|watchdog` picks the path; asking for systemd where it does not work fails rather than falling back.
- **Upgrade:** zero manual edits. Move the pin, run `eng sync` (AGENTS.md changes), commit. No config key is required; `verification.parallel` is optional and off, so checks run one after another exactly as before. Every check that ran before still runs: an undeclared check is light, so it runs in every stage, under the default budget. A check that needs more than 2 GB, more than 30 minutes, or raw java/gradle in its script now fails loudly; declare `# budget:` (or pass the bound) in that script. A check that leaves a background process running now waits for it (up to its timeout) instead of passing past it.

## 0.13.0 (6 Nov 2026)

**Verification tooling decides, not who ran it** (Matt, 6 Nov 2026; Core decisions nd716pq0vffa13z4c99e09552x8hqwp3 and nd71bs9kx7rnwphcj0jhp50b1n8hpk4d). Verification tooling shows a change is sound. It is its own dimension, so the builder may verify its own work. This returns to the 28 Oct agreement and supersedes the 3 Nov wording that the required check is a verdict from someone who is not an author. Model review stays a tool: required only for text no check can run, and optional elsewhere.

- **`eng verdict round --by <id> -- <cmd>`** records the run as that verifier's evidence: the command, its exit code, the last 2000 characters of output and the commit SHA, in the clone's git common dir (`eng/verdict-runs.jsonl`). `--by` names the verifier (a tool, lane or agent, the builder included). Without `--by` a round works as before and records nothing.
- **`eng verdict PASS|PASS+NOTES|FAIL --by <id>`** records `method: verification` and attaches that verifier's runs on HEAD. A PASS needs at least one run, and every run must exit 0. **`--review`** records `method: review`. The PR comment lists the runs.
- **One rule in all three gates** (`lib/verification.mjs`, used by `eng verdict check`, self-merge and `eng merge gate`). An unknown or incomplete file list counts as testable. Any FAIL blocks, a review FAIL included.

- **A verdict counts only for the exact commit it ran on** (PR #42 review). `eng verdict check`, the renovation refresh plan and receipt, and `eng merge gate` for a queue-mode PR no longer carry a verdict by patch-id, which ignores the commit message and whitespace: a message-only amend or a whitespace-only change used to keep a PASS for an untested SHA. A rebase or a merge-in of the base now needs a new run and verdict. `verdict_carry` is still accepted but no longer carries. The one exception is GitHub's merge_group commit, which no verifier can run first: its verdict must be for the exact PR head that was queued, and the queued commit must carry the same patch-id.
- **Old failures no longer age out** (PR #42 review). The evidence for a commit and verifier is the latest run of each distinct command, with no 20-run window. A failing command stays failing until that same command passes again; other passing commands never hide it.

## 0.12.5 (4 Nov 2026)

**A short socket folder per run, and an opt-in private network** (Motus Lead, 4 Nov 2026; Eng Manager Core task p5711dqnz7m50h56b2jg4kaffh8hcmtv). Motus PR470 had 51 tests and its `ephemeral:launch` failing under 0.12.x, for two reasons. First, every `eng ephemeral` run's TMPDIR is about 98 bytes on the devbox, so the unix sockets its tests bind went past the 107-byte cap. Second, the run's bwrap stops a nested bwrap. On a host with `kernel.apparmor_restrict_unprivileged_userns=1` (Ubuntu 24.04), whatever runs under bwrap is confined to AppArmor's `unpriv_bwrap` profile, which denies every capability. So a test that starts its own `bwrap --unshare-net` fails with "No permissions to create new namespace". Neither host AppArmor nor eng's sandbox changes.

- **`ENG_SOCK_DIR`.** Every `eng ephemeral` run (and every `eng gate` step it wraps) gets `ENG_SOCK_DIR=$HOME/.cache/eng/s/<first 8 hex of sha256(ENG_RUN_ID)>`, mode 0700. On the devbox that is 31 bytes (`/home/dev/.cache/eng/s/xxxxxxxx`), whatever the run id; a nested run's folder sits inside its parent's, at 40. Bind unix sockets there. A container's bind mount resolves it at the same path, because the docker daemon sees it on the host, which the run's private `/tmp` is not. eng sets the variable only when the folder is under 60 bytes, in a home this user owns outside `/tmp`, so code that reads it needs a fallback. It is under `$HOME`, not `XDG_CACHE_HOME`, so its length is fixed per user. It is not under `$XDG_RUNTIME_DIR`, which holds the docker socket: devbox-ops' heavy-lane docker proxy (`workspace heavy run`) refuses any bind from there.
- The folder belongs to one run. eng creates it, never reuses it (an existing one is an error), writes the run id to `ENG_SOCK_DIR/.eng-run`, and removes it with the run's round, on a pass, a failure or SIGINT/SIGTERM/SIGHUP. Inside the run's bwrap, `$HOME/.cache/eng/s` is an empty tmpfs with only this run's folder bound back, so a run does not see another run's folder at its path, and `.eng-run` is read-only. Like the rest of enforcement (0.12.2), this guards against accidental cross-run use, not a deliberate one: the same user can still reach another run's folder through `/proc/<pid>/root`. Under `isolation.mode: fail` the folder stays writable, and the run's docker socket lets a container bind it, although the rest of `~/.cache` is read-only. A run killed with SIGKILL leaves its folder; the next `eng ephemeral` run removes it once that run's eng process is gone, as does `eng clean --apply`, which also removes an ownerless one older than `--older-than`.
- **`isolation.network: private`** (default `host`). The run's bwrap also unshares the network namespace. The run has loopback only: a server on the host's 127.0.0.1 is refused, any other address is unreachable (`ENETUNREACH`), and it cannot reach a host server on an abstract-namespace socket either, which closes that limit of enforced isolation (0.12.2). Filesystem sockets still work, so `DOCKER_HOST` (the run's labelling docker socket) and `ENG_SOCK_DIR` keep working. Containers the run starts keep docker's own network. The run gets `ENG_NETWORK_ISOLATED=1`, so a tool that would start its own network sandbox can see the outer one and not nest a second bwrap. eng never passes an inherited `ENG_SOCK_DIR` or `ENG_NETWORK_ISOLATED` on: it sets both itself.
- A run that would get no network namespace (no usable bwrap, or a run folder under `/tmp`) is refused before it starts, in every mode. Like `isolation.mode: fail`, the switch makes the check strict and keeps runs watched when `ephemeral_runs.mode` is off, in `eng ephemeral` and `eng gate`. It adds to `isolation.mode`, and replaces nothing. In warn mode the run can still use this user's other filesystem sockets (the systemd user bus, tmux, agents), and through them the network. `isolation.mode: fail` covers those too.
- `eng` rejects any other `isolation.network` value. The starter config, the README, `docs/project-isolation.md`, the launch contract and the eng-verify skill describe both. Consuming repos see an eng-verify skill diff on their next `eng sync`.

## 0.12.2 (2 Nov 2026)

**Isolation fixes before enforcement** (Matt, 1 Nov 2026: devbox project isolation will be enforced; Core decision nd74kgtnr9qpq1ztyrasyt84518ha76q). A TLA+ model of devbox run isolation (eng-sandbox PR #19) found the holes. The first two items below (what counts as permanent, and `eng clean --containers`) apply in every mode. Everything else is enforcement, which changes nothing in warn mode, the default. Enforcement is `isolation.mode: fail`, which each repo's lead turns on. Threat model: enforcement stops an honest agent from accidentally using or damaging another project's containers, temp files, caches or Convex deployment; it is not a sandbox against deliberate escape, and the hard boundary (rootless Docker or a per-project Unix user or user namespace per run) is a devbox-ops follow-up.

- **One meaning of permanent.** A container is permanent when it has the persist label (`slaytek.persist=true`) or a restart policy other than `no`, as devbox-ops docker-ephemeral already treats it (`permanent()` in `lib/ephemeral.mjs`). `eng ephemeral` used to `docker rm -f` a restart-policy container a run made. It now keeps it. `slaytek.persist=true` counts even in a repo that sets its own `persist_label`, since it is the devbox-wide marker.
- **`eng clean --containers --apply` keeps permanent containers**, a volume with the persist label, and the volumes a permanent container uses. It also keeps a repo volume that a container it does not remove still uses, and drops `-v` for a container whose anonymous volume is marked. It removed every container and volume with the repo label, marked or not.
- **`isolation.mode: fail` enforces isolation in `eng ephemeral`** (CI and `eng gate`), whatever `ephemeral_runs.mode` says. A run with no private `/tmp` is refused. `/dev/shm` is private. `~/.convex` and the cache home are read-only inside the run, except the checkout, the run folder, this repo's eng caches and the pinned download cache, and one of them that appears fails the run. An unlabelled, non-permanent container made during the run fails it, as does a process started in the checkout outside the run's process tree (a tmux server that was already running). Neither is removed or signalled.
- Under enforcement, `ephemeral_runs.mode: off` no longer skips the watched run (in `eng ephemeral` and `eng gate`). The run's docker socket refuses a writable bind mount of `~/.convex` or the cache home, since Docker mounts outside the sandbox. A failed inspect of an unlabelled container makes the run not fully watched, not a pass. A process started under a tmux or screen server older than the run counts as a stray wherever its cwd is, and any change under `~/.convex` (snapshotted before and after) fails the run, whatever made it.
- Under enforcement, the sockets of servers older than the run (this user's filesystem sockets, and the rootful docker socket) are covered inside the run, so it cannot start or write anything outside the sandbox through them. Enforced runs therefore get no ssh-agent, gpg-agent, systemd user bus or existing tmux, with no per-repo allowlist; git over ssh and signing happen outside them (Core decision nd70c9mympghhypt8ca4mkk3t18hazbe). Accepted limits (Core decision nd746n3mew9ek2j7bsdhd586bs8hax9m), with a per-run Unix user or network namespace as the devbox-ops follow-up: abstract-namespace sockets, and another name for a socket (a relative bind path or a hard link), are not covered. A write through a symlink inside `~/.cache` lands at its target and is accepted.
- Under enforcement, the run's docker socket also refuses `exec`, `start`, `cp`, `attach` or `rm` on a container it did not make and any prune, and the raw upstream socket is hidden. A leftover container whose volume labels cannot be read is removed without `-v`. A bind source that does not exist yet is resolved through its symlinked parents, and starting an exec is checked against its container. Connecting a container to a network, or disconnecting it, is refused unless the run made both the network and the container. A container may not mount a server socket outside the run (the daemon's own, any socket hidden from the run, or a folder holding one), read-only or not; the run's own labelling socket can still be mounted. eng's own caches (this repo's, every cache `hygiene.caches` points elsewhere, and the pinned download cache) are created before the run and stay writable, on a fresh runner too. When the run's docker socket cannot look up an object's owner or a volume's mounts (any answer but found or gone), it refuses the request instead of forwarding it. It reads requests as Docker does: a path in another form (percent-encoded, doubled or dotted) is refused, as is a body whose checked field is spelled in another case or holds a non-ASCII key Go would fold (`ſ`, the Kelvin sign), and it forwards exactly the JSON it checked. An attach to a container the run did not make is refused over any method, websocket GET included. Only attach and exec start may upgrade a connection, and only after Docker answers 101 is it piped both ways. A container may not share host or container namespaces (PID, IPC, network, UTS, user, cgroup), run privileged, loosen its security profile, or add a capability outside an allow-list, so BuildKit builds and `network_mode: host` do not run in enforced runs. Images are not guarded: an enforced run can still remove or commit to an image it did not make. The run's docker socket also refuses parent-folder binds, bind-backed volumes and `--volumes-from` that would write protected home state. A `~/.convex` with a symlink in it is refused, and one that grows past the 20000-entry snapshot limit during the run fails it. A run container removed as a leftover keeps an anonymous volume marked `slaytek.persist=true`.
- **New isolation rule `convex-url`.** A service that runs a convex program must set `connect_env = { CONVEX_SELF_HOSTED_URL = "http://127.0.0.1:{port}" }`, so `eng connect` clients reach the backend eng started, not one found by deployment name. With `isolation.mode: fail`, `eng connect` refuses a `.connect.env` that sets that variable when `connect_env` pins it. It warns in warn mode and fails in fail mode, like every rule. The starter `templates/isolation/project.toml` sets it.
- An unnamed compose file already failed `eng isolation check` in fail mode. A test now pins that.

**Self-merge runs on events and merges without a wait** (Matt, 26 Oct 2026: "No wait. Merge as soon as it's verified; post-merge checks roll back breakage.").

- `self-merge.yml` has no schedule. The 30-minute cron from PR #17 is gone. It runs when `ci` finishes, on a verdict comment or `verdict` status, when a label is added or removed, when a PR is marked ready or retargeted to main, and on dispatch. Each event looks at its own PR. Runs queue one at a time (`queue: max`, up to 100 waiting), so two merges never run at once and a newer run never replaces a waiting one.

The post-merge check and auto-revert are otherwise unchanged. An auto-revert whose inverse restores a `ci.yml` without that job says in its PR body how to start self-merge by hand.

**Verifier independence is judged by identity** (approved by Matt, 26 Oct 2026). Models and providers are not part of the engineering standard. Supersedes PR #23.

- A verifier counts only when its identity (`eng verdict --by`, plus its GitHub login when `verifier_logins` is set) equals no author's identity: `Agent:` trailer ids, commit author and committer emails, and commit GitHub logins.
- risk:high (self-merge) needs PASSes on the exact head from `ship.high_risk.verifiers` (default 2) independent verifiers with distinct identities. `eng merge gate`: `merge.auto.high_risk_paths` and `merge.auto.high_risk_verifiers` (default 2) replace `second_provider_paths`, which now fails validation with a rename message. The gate's restart cause `second-provider` is now `verifiers`.
- `verifier_logins` (`ship.self_merge` and `merge.auto`) is a list of logins. Each login is one identity.
- `eng verdict` drops `--family`, `--provider` and `--model`, and fails if one is passed. Verdict records and comments carry no family or provider. Older verdict comments with those fields still parse; the fields are ignored. `Agent-Family:` trailers are no longer read.

  - In strict mode it updates a behind PR that has auto-merge on.
